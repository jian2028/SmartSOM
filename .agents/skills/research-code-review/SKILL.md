# 科研软件多 agent Code Review

采用通用工程审查与科研软件验证原则，不固定 SmartSOM 的模块、算法、目录或既有设计。用户批准的新需求和重构目标是本次验收依据；仍然适用的项目指令照常遵守，冲突应明确指出。

## 触发与边界

- 在 SmartSOM 完成一个可独立审查的逻辑改动后、报告完成前运行；不在每次保存文件后重复启动。
- 支持两种模式：开发任务内闭环（审查、修复、复核、测试）；独立只读审查（仅报告，不擅自修复）。按用户当前授权选择。
- 其他项目仅在用户明确调用本 skill 时运行。纯文档或注释修改用相应轻量检查；涉及可执行示例、公共行为说明或科研结论时评估实际风险。
- skill 是执行指引，不是文件监听器或强制 CI。项目级常态触发由项目指令关联；不自动获得提交、推送、部署共享环境、长训练或正式实验的授权。

## 1. 确认需求与审查对象

沿用已确认需求，简述预期行为、验收条件、允许改变的语义、须保持的行为和范围外事项。只问影响正确性或授权范围的未决问题。

读取当前 checkout、适用指令和 `git status --short --branch`。区分任务开始前已有修改、本任务修改及交叉影响；任务中途接手而无基线时，不臆测哪些修改属于本任务。

送审材料包含：需求、受影响入口与调用者、完整相关实现、测试和必要契约，以及明确的比较基线。包含相关 staged、unstaged 和未跟踪文件，不能只看 `git diff HEAD` 而漏掉新文件。

记录本次审查版本：commit + dirty 状态 + 范围内文件内容摘要/哈希（包括新增文件）；大改动按独立职责分批，并补接口集成审查。审查期间协调停止对目标文件的写入，或提供包含实际未提交改动的独立快照；单纯 checkout HEAD 不代表脏工作区。来源变化后，旧审查结论不自动覆盖新内容。

## 2. 开发者自查

本节的代码修改仅适用于闭环开发模式。只读模式检查现有自查证据，必要时可在不会修改共享文件或触发外部副作用的隔离环境执行验证；禁止自动修复、格式化写回和删除代码。

在并行审查前运行项目已有的格式、lint、类型检查及相关快速测试，按实际工具链选取，不擅自安装整套新工具或强加覆盖率门槛。记录命令、退出状态及未通过/未运行项。缺陷测试应验证可观察行为，不抄写实现；低影响可逆改动无需为了流程编写测试。

闭环开发模式下，送审前自查删除无用代码、调试残留和不必要复杂度。已知失败应附证据和基线，不能让 reviewer 把测试未执行理解为通过。

## 2.1 每轮性能回归检查

SmartSOM 每轮可审查的代码、测试或运行配置改动，都调用同目录的 [evaluation-profile](../evaluation-profile/SKILL.md)，完成一次改动前后的性能对照，再汇总审查结论。这是当前 code review 的子步骤；profile 返回后继续本轮审查，不递归启动另一轮 review。纯文字修改仍按前述轻量检查；测量工具本身的改动也要验证不会影响被测执行路径。

- 基线选本轮改动前的稳定版本，记录它与 main 的关系；使用独立 checkout，并固定 checkpoint、场景/种子、线程、指标、终止条件与机器。至少选一个代表性用例，按受影响路径增加 Base/SL、规模或条件；不为获取基准而启动训练。
- 默认串行交替运行至少 3 次无 profiler 的对照，用各自 wall-time 中位数比较，附原始值/范围。setup、仿真主体、UI/追踪等计时边界必须一致，不能把未完成或少做工作的运行当作加速。
- 耗时增幅 = `(改后中位耗时 / 改前中位耗时 - 1) × 100%`。任一代表性用例**超过 5%**，明确标为“性能回归需关注”，不能用其他用例的加速平均掉。`compare_cases.py` 的 `performance_check` 会记录该提醒；等于 5% 不触发。
- 触发提醒后，核查工作量、来源、后台负载及测量波动，必要时重复受影响对照，再单独运行 phases/cProfile 定位。报告退化幅度、热点、原因及处置：修复已授权范围内的非预期开销，或说明已批准功能带来的成本。5% 是关注阈值，不是自动拒绝功能或新增审批要求；结果不一致仍按正确性缺陷处理。
- 行为保持改动比较完整语义报告及相关轨迹；已批准的语义变化另行定义验收，不能删除差异来凑出“等价”。缺基线、checkpoint、依赖或可比条件时明确记为未测与缺口，不能用单次耗时或单元测试通过代替性能结论。
- 送审证据包含源码身份、计时范围、重复次数、中位数/范围、增幅、5% 提醒及结果等价性。测试 reviewer 独立核验测量方法；修复后只重测受影响用例。profiling-only 的只读边界和原有授权继续有效。

## 3. 独立多 agent 审查

使用当前环境的 subagent/delegation 工具，至少两名独立 reviewer；通常三名。主 agent 负责协调、验证发现及实施已授权修复，不把自己的自查算作独立 review。并行受可用槽位约束，可分批完成；工具不可用时标记多 agent 审查未完成，不能以角色扮演代替。

| Reviewer | 必查责任 |
| --- | --- |
| 工程正确性与简洁性 | 需求符合性、调用链、边界、异常、状态和并发；冗余、过度抽象、过度防御、设计引入的成本 |
| 科研语义与可复现性 | 数学/仿真语义、信息可见性、随机性、指标口径、对照公平性、来源与结果证据 |
| 测试与运行验证 | 测试能否揭露错误、独立预期值、回归风险、安装与入口、失败恢复、跨环境必要性 |

很小且不涉及科研语义的改动可用工程 reviewer + 测试 reviewer，并说明科研项不适用；涉及模型、指标、实验、随机性或仿真状态时使用三类审查。复杂度、性能、外部输入、安全或 UI 风险较大时，在可用槽位内增派专项 reviewer 或安排第二批。无相关变化不做全仓安全审计。

每位 reviewer 先独立判断：只提供同一份需求、代码与原始证据，不预先提供主 agent 的疑似结论或其他 reviewer 的发现。工具支持时以空白历史启动（`spawn_agent` 使用 `fork_turns="none"`），显式提供必要需求和适用指令；无法隔离历史时披露独立性限制。共享工作区 reviewer 只读；需写独立探针/测试时使用自己的隔离目录或 checkout，禁止改动共享源码、测试及实验输出。独立副本必须包含实际待审补丁。

派发时明确：角色、范围、审查版本、验收要求、适用专题、写入边界及预期输出。要求检查必要调用者/被调用者，而非只读 diff。返回已查范围、未查范围、发现及证据；允许零发现，不设置找 bug 配额。多个相同模型的同意不构成正确性证明。

工程 reviewer 必须读取 [复杂度与性能审查](references/design-costs.md)。涉及科研行为时，科研与测试 reviewer 读取 [科研验证](references/research-validation.md)。

## 4. 验证、去重与修复

每条缺陷包含：ID、优先级、文件与精确行号、触发条件、证据或可执行复现、后果、最小修复建议、验证方法。证据不充分时列为“待验证”，不要当作确认缺陷。复杂度建议还须说明维护/运行成本，以及更简单方案会保留或失去什么。

- P0：应立即停止推进的严重数据破坏、安全或不可恢复错误。
- P1：主要功能、研究语义或结果有效性受到实质损害。
- P2：已确认但影响受限的功能、维护性或性能问题。
- P3：可选改进；个人风格偏好不作为阻塞项。

严重性按触发条件、影响范围和证据裁定，不按多数票或机械取最高级。相同根因合并，保留受影响位置；争议通过调用链、规格或最小复现解决。历史问题独立记录，只有本次引入、暴露或影响验收的问题进入本次修复范围。

闭环模式下主 agent 修复授权范围内的确认缺陷，补适当回归检查。只读模式不执行修复和部署；可按委托在隔离环境完成无项目副作用的必要验证，未发生修复时“修复复核”标为不适用。改变研究假设、公共契约、兼容策略或扩大重构范围时，先呈现证据与具体选项再请求决定。

## 5. 独立复核与交叉测试

修复后记录新版本与增量，原 reviewer 或另一独立 reviewer 复核受影响发现、调用链及新风险；主 agent 不能仅凭“已改”关闭问题。重跑失败用例和受影响检查；无新变化或风险时不重复全套测试。

“测试环境部署”按改动需求选择：纯库/算法可用隔离本地环境；安装、打包、CLI、服务或 UI 改动需要相应真实入口；涉及平台特性才增加目标平台测试。环境准备须匹配被审版本和依赖，记录关键配置；缺硬件或权限即标记覆盖缺口，不能模拟宣称通过。

由非实现者从验收条件推导至少一个相关场景，不只复跑实现者写的测试。按风险选手算小例、独立参考、边界/异常、性质/变形、差分或端到端验证；不要求每次全部执行。可复用测试 reviewer 做此阶段，但应给其独立设计预期结果的空间。

修复循环持续到阻塞项解决；若同一问题反复出现、证据矛盾、修复须扩大范围或超出已约定预算，汇总根因和待决定事项，不无限循环，也不把未完成项标通过。

## 6. 验收与报告

只读委托的结论限定为“审查结论”，按委托范围判断完成；未授权的修复或部署不适用，不因此将只读审查永久标为未完成，也不得暗示开发闭环已经验收。委托所需的验证缺失仍应标记未完成。

核对最后测试和审查对应最终文件版本；后续编辑使受影响结论失效，补增量复核。结论只能为：

- **通过**：适用验收条件、独立审查及必要检查均有完成证据，无未解决 P0/P1/P2 缺陷；可有明确列出的 P3 可选建议。
- **有条件通过**：必要验收条件已验证，仅保留不违反这些条件的 P2 缺陷；明确影响、处置和用户已接受的风险。未经接受不得自行使用此结论。
- **需修改**：确认存在 P0/P1、违反必要验收条件的问题，或尚未解决/获准保留的 P2 缺陷。
- **未完成**：必要审查/验证/平台缺失，或关键不确定性尚未解决。

普通“通过”也须显式列出所有未解决的非阻塞建议；不能通过降级严重性规避验收。工程通过不等于科学假设成立、算法优于基线或结果可独立复现；没有正式实验依据就不作此类结论。

用用户语言简洁报告：审查范围/版本 → reviewer 实际完成情况 → 关键发现与修复/复核状态 → 测试命令及结果 → 性能基线/耗时变化/5%提醒 → 遗留和最终结论。按需要在项目允许的本地产物目录保留报告，不自动提交报告或实验产物。

## 依据与适用方式

本 skill 的角色分工、优先级和触发规则是为用户设计的执行方案，不声称是某个机构规定的多 agent 标准。

- [Google：审查内容](https://google.github.io/eng-practices/review/reviewer/looking-for.html)：设计、功能、复杂度、测试及上下文。
- [Google：审查标准](https://google.github.io/eng-practices/review/reviewer/standard.html)：持续改善代码质量，避免为追求完美阻碍合理改动。
- [JOSS：软件审查标准](https://joss.readthedocs.io/en/latest/review_criteria.html)：安装、实际功能、验证方式及文档。论文投稿资格要求不作为日常代码门槛。
- [ACM SIGOPS：Artifact Evaluation 经验](https://www.sigops.org/2025/lessons-from-five-years-of-artifact-evaluation-at-eurosys/)：可运行软件产物与研究结果验证分别取证；本流程不授予学术认证。
