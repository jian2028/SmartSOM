# AI coding 冗余、过度设计、过度防御与性能成本

审查目标是以较低的理解、维护与运行成本满足当前已确认需求。不能仅因代码由 AI 编写、存在抽象或有防护就判错；也不能把“更少代码”当作唯一目标。

## 冗余与过度设计

检查新增或扩大的重复逻辑、只转发的层、一次性抽象、通用框架、注册器、工厂、配置开关、可选分支、兼容层和死代码。逐项追问：

1. 当前哪些调用者/需求确实使用它？真实约束是依赖隔离、接口稳定、测试替身，还是只有假设中的未来扩展？
2. 增加多少概念、状态、隐式依赖和调试跳转？重复逻辑是否可能产生语义漂移？
3. 直接函数、明确数据结构或较少层次能否完整满足需求？删除后会失去哪些已承诺能力？

单一实现的接口、较长文件或少量重复本身不构成缺陷；不因减少重复而强行合并语义不同的代码。不擅自移除仍有真实消费者的兼容行为。

## 过度防御

重点追踪：

- 同一可信数据经过每一内部层都重新完整校验；已验证对象仍反复序列化/反序列化。
- `except Exception` 吞错、返回空结果/零值/默认成功、静默回退到另一算法或配置，导致结果看似正常。
- 对确定性错误重试，无上限重试，无幂等保障的写操作重试，嵌套重试放大时延。
- 不可能状态被转换成“继续运行”；多套 fallback、重复状态检查或锁没有对应失败模式。

先标出信任边界、对象可变性和所有权。外部配置、文件、网络、进程间输入、合法并发竞争、持久化恢复及会被修改的对象可能需要再次检查。删除重复防护应保留合适边界的验证与明确失败行为；不能为了速度牺牲真实性或数据完整性。

## 设计引入的性能成本

沿一条真实执行路径累计成本：调用频率 × 单次工作量 × 数据规模。检查循环内全量遍历、重复派生值、深拷贝、对象/张量分配、格式转换、序列化、磁盘写入、同步点、锁竞争、过密日志和过多小任务。

区分三种证据：

- **已确认结构性成本**：代码可证明重复扫描或复杂度增长；说明规模和适用条件，不能据此杜撰耗时。
- **疑似运行瓶颈**：有合理机制但尚未测量；提出小规模对照探针。
- **已测性能退化**：同工作负载、规模、依赖、硬件和计量口径下，有基线与改后数据；记录端到端时间/吞吐、必要的内存与剖析证据。处理预热和测量波动。

缓存、批处理、并发和向量化也有一致性、失效、内存和调度成本，不能一律作为修复。性能优化须先验证输出/语义符合约定，再评价收益；没有明确需求时不自创硬性性能阈值。

## 发现的最小形式

位置与调用链 → 真实需求/边界 → 具体复杂度或运行代价 → 证据强度 → 简化方案与代价 → 验证方法。

没有可说明的代价或收益时，将偏好保留为可选建议。格式、命名、行数和抽象数量不能代替工程判断。
