# Code Review

以用户已确认的需求为验收依据。目标是发现会改变行为、结果或维护成本的问题；不追求评论数量，也不把个人风格偏好当作缺陷。

## 触发与范围

- 在 SmartSOM 完成一个可独立审查的逻辑改动后、报告完成前使用；不在每次保存文件后重复调用。纯讨论、状态查询和读取结果不触发开发审查。
- 区分开发闭环与只读审查：前者可在原授权内修复；后者只给发现与证据，不自动修改文件、启动实验或部署。
- 用户指定的范围、预算与代理限制优先。本 skill 不授予提交、推送、长训练、正式实验或联系他人的权限，也不覆盖必需的仓库 CI。

## 阶段一：确定风险与范围

读适用指令和 `git status --short --branch`，确定基线、相关 staged/unstaged/新增文件及关键调用者。区分已有工作与本次改动。用一句话说明选定级别和原因；不必让用户逐次批准常规分级。

按行为影响、失败后果和耦合程度分级，**不按行数、文件数量或“只改 YAML”机械判断**。下面数量为主 agent 之外的独立 reviewer 数：

| 级别 | 适用范围 | 默认审查投入 | 验证范围 |
|---|---|---|---|
| L0 轻量 | 无行为变化的文字、格式、局部命名或机械改动，且已确认没有接口、动态引用或配置含义变化 | 0：主 agent 自查 | 差异、链接/格式；必要时相关现有检查 |
| L1 标准 | 边界清楚的局部功能、输入校验、普通 bugfix、局部重构；不涉及下列高风险契约 | 1：工程与测试合并审查 | 相关调用链和针对性测试；必要时真实入口 |
| L2 深入 | 并发、调度/资源保护、失败恢复、持久化/checkpoint、兼容迁移、权限/删除等重要边界；模型/奖励/终止/随机性/数据划分/指标语义；跨模块重构或影响范围尚未厘清 | 2：按风险分工 | 契约/异常/回归及适用的差分、集成或性能验证 |

L2 通常分为“实现与状态/接口”和“独立验证与结果语义”；涉及科研语义时，后者须覆盖科研契约，不另默认增加第三人。不因为项目属于科研软件就把所有改动升为 L2。

审查发现实际影响超出原边界时再升级。升到 L2 时保留原 reviewer，只补缺失职责；不要从头再派两人。默认每个逻辑改动最多 2 名 reviewer，不允许 reviewer 自行再委派。只有用户明确要求更多审查者时才扩展人数；复杂任务优先缩小或拆分审查范围，并检查分块接口。

若当前对话禁止子代理或工具不可用，遵守限制，完成可做的自查和测试，明确“L1/L2 独立审查未完成”。不以角色扮演替代，不为省 token 把高风险改动伪装成 L0，也不因此停止其他已授权开发。

## 阶段二：自查与针对性验证

先检查需求是否满足、关键状态/边界、失败行为、无用代码及不必要复杂度。只运行与改动有关的格式、lint、类型和测试，再按失败、风险或仓库要求扩大。低影响可逆改动不为走流程新增测试；新增缺陷测试应验证外部行为，不能用被测实现生成 expected。

- 涉及新增抽象、重复校验、重试、缓存或复杂度争议时，读 [设计成本](references/design-costs.md)。
- 涉及科研语义、指标、实验公平性、随机性或语义保持重构时，读 [科研验证](references/research-validation.md)。
- **性能验证按需触发**：改动热路径、I/O、分配、缓存、并行/采样/资源调度，声称性能改善，或已有耗时回归证据时才测。UI 文案、普通冷路径校验和无运行影响的修改不默认跑仿真性能对照。
- 先选最小且有代表性的测量。SmartSOM 的评估性能问题在本地存在 `evaluation-profile` skill 时使用它；其他路径用适合该路径的基线对照。记录相同负载、版本、计时范围和重复测量；已有性能门槛继续适用，但不把某个 benchmark 的门槛扩展成所有修改的准入门槛。
- 正确性检查通过才解读速度收益。已有结果充分且本次没有相关变化时复用证据，不重复完整面板或长训练。当前授权不足以安全测量时，记录具体缺口。

## 阶段三：分级审查

L0 到此由主 agent 完成自查，不要求独立 reviewer。L1/L2 在允许委派时执行：

1. 记录实际待审版本（基线、脏状态、范围内内容摘要/哈希，包含新增文件）。若代码仍在变化，使用包含补丁的只读快照；不能把干净 HEAD 当作未提交改动。
2. 给 reviewer 必要需求、受影响文件/契约、相关调用者和原始验证证据，不复制完整聊天或全仓文件。可以按证据追到关键依赖，不限制到只看 diff。默认不联网，不重复生成实现者已有摘要。
3. L1 一名 reviewer 合并工程与测试视角；L2 两人分开职责，交叉关注共享边界。先各自判断，不提前提供另一人的结论或主 agent 的嫌疑清单。
4. reviewer 只读共享源码；需独立探针时用隔离目录，且不启动昂贵任务。工具支持时使用最小上下文的新会话；不可隔离则披露限制。
5. 输出优先级、具体位置、触发条件、后果及证据；再简述已查范围和真实缺口。允许零发现，不凑 bug、不重复列长检查清单。L1/L2 至少由一名非实现者从需求推导一个相关边界/失败场景，能运行则运行，不能运行时明确区分推理与执行。

## 阶段四：增量复核与停止

合并重复发现并核实，不按多数票定严重性。P0/P1 是严重正确性、数据安全或结果有效性问题；P2 是已确认的局部功能/维护问题；P3 是非阻塞建议。证据不足的疑点标为待核实，不能包装成确认缺陷。

开发任务只修复授权范围内的问题；只读任务在报告发现后结束，不因没有代为修复而判任务未完成。修复后优先由原 reviewer 复核受影响的增量并重跑相关检查；新变更影响已有结论时才重审对应部分。只有范围/契约实质改变或出现系统性遗漏才重开完整审查。

相关验收满足、实质发现已处理且验证完成后停止。未解决的问题明确列出，不能靠降低严重性或省略检查宣布通过；重复争议用具体测试/规格解决，不无限增加 agent 或重跑全仓测试。

按“已选级别、实际投入、关键发现、验证结果、缺口”简洁汇报。明确区分自查、独立审查和实际测试；L0 可以在其范围内完成而不需要独立 reviewer。通过工程审查不意味着算法优于基线、科研结论成立或独立复现完成。

分级依据和边界示例见 [设计依据](references/review-design.md)，仅在调整分级或需要解释依据时读取。
