# v2诊断 · 中图

状态：已生成 25 个官方入口实验配置和中图评估面板。用户已授权服务器
中图与 Mac 小图并行诊断；先短验证，后长训练，不另设一套算法假设。

## 固定设置

- 场景基线：`configs/scenarios/v2/medium.yaml`。20 台机器、25 辆 AGV、
  750 个订单（初始 100），机器 PRE/POST buffer 容量均为 4。
- 保留该场景的 Job 路线分布、重复工序概率、加工时间、交期、到达过程、
  故障及质量参数；不能用小图的订单数或评估世界哈希替换中图。
- Base DDQN，各实体参数 independent，训练 seed 101 优先；奖励、Mover、
  规则集合及优化器参数沿用小图诊断的对应对照。容量相关维度必须由中图
  实体构建，不能复制小图的网络数或 checkpoint。
- 训练 normal/low/medium/high 均衡循环。短验证每组 8 个完整 episode；
  长验证每组 1000 episode，250/500/1000 做固定面板验证。
  train_ticks=100000、drain_ticks=10000、complete_episode，与原中图一致。
- 原语义与窗口语义比较采用相同 packed replay 存储及审计实现，避免将
  存储后端差异混入算法对照。不改变旧中图训练或迁移其恢复文件。

## 三阶段对照

| 阶段 | 对照 | 回答的问题 |
| --- | --- | --- |
| 1：学习链路 | 原始语义 vs 显式窗口终止语义 | 最后一次决策的尾部奖励是否进入 replay；改变窗口目标能否改善学习？ |
| 2：状态信息 | 同一终止语义下，原观测 vs 原观测加全局压力 | 局部信息不足是否造成取货和缓冲协调失败？ |
| 3：取货策略 | 学得取货 vs HPOF/NPF 固定取货 vs 仅 BLOCKED 输出优先 | 输出疏通是否是性能瓶颈；何种干预代价更小？ |

阶段 1 记录每个主体（Dispatcher 分 stage）的最后动作、尾部 tick、
奖励、写入/遗漏数量和终止原因。窗口处理仅针对 drain_deadline，
不把预算截断或墙钟中断伪装为自然终止。它改变学习目标，不能仅凭性能
改善就称原实现有 bug；参见 ADR0081。

阶段 2 复用小图的四项公共全局统计：阻塞机器比例、平均 POST 占用率、
有待取货且无车辆承诺的 POST 比例、载货 AGV 比例。对照只增加这些输入，
不改变奖励或动作。记录中图候选 padding、有效 mask 和实体覆盖，确认无
小图尺寸硬编码。分别在原语义和窗口语义下配对，避免混淆两个改动。

阶段 3 的 HPOF/NPF 定义为：存在 HPOF 可选输出时用 HPOF，否则用 NPF；
不能仅保留 HPOF 而导致开局无输出时无动作。BLOCKED 优先只筛选已有合法
候选，没有该类候选时保留原集合，不放宽容量约束。

阶段 3 分两类证据：

1. 同一完成 checkpoint、同一评估世界和动作种子，仅替换取货决策，其余
   角色保持网络控制，不重新训练。这检验当下取货决策的影响。
2. 从头训练上述三个取货方案，保持其余设置一致。这检验长期适应效果。

两类结果分表呈现，不能把固定规则推理干预称为重新训练后的提升。
原观测及压力观测下的取货消融保持配对。阶段间可并行独立对照，但每个
组合须明确变量；不因小图的早期表现就删去中图原语义对照。

## 评估与判读

中图独立生成 validation 32 例（每条件 8）和 test 80 例（每条件 20），
为中图场景重新计算世界哈希，核验与训练世界无交集。跨规模保留相同
面板种子用于配对，但物理世界不同，不能视为相同世界。所有方案与 Justin
使用相同面板。面板定义归入本目录的 panels，不能直接复制小图哈希。

报告 completion、observed overdue/order、reward、质量、机器 processing /
blocked / starved 时间比例，以及完成世界的 mean tardiness。未完成订单
不按 tardiness=0；条件性的完工 tardiness 必须同时报告样本量及完成率。
跨方法只有完成样本集合相同时才直接比较该条件均值。

验证时同时看完成率、逾期和利用率，不以利用率单指标挑选赢家。先排除
明显不完工方案，再比较完整性相近方案的逾期与质量，利用率用于解释；
存在互有优劣时保留多个方案，不事后改权重构造单一分数。固定使用
1000 episode checkpoint 作最终比较；250/500 用于看学习曲线，不择优
替代最终 checkpoint。最终 test 不用于选择方案。seed 101 结论只属于
单 seed 诊断，若需稳定性结论，再以 102/103 配对复核。

## 实现与启动顺序

1. 确认小图通过官方入口实际推进，完成相关组件短验证。
2. 在本目录生成与小图对应的 stage1/2/3 变体及独立面板；相对路径指向
   中图场景。通过现有 YAML 和组件扩展接口复用已验证逻辑。
3. 使用官方 smartsom check 检查整个中图目录；在服务器做短验证、
   checkpoint 恢复验证和资源测量后，按明确变体选择运行长实验。
4. 优先使用官方 run/pause/resume；不需要新增顶层命令或替换调度器。
   checkpoint 单独换取货规则的评估如缺受支持入口，应先说明具体缺口，
   再扩展已有评估类别，不能私下绕开来源/模型兼容性验证。

中图并发由服务器当前 CPU、内存和总 tick/min 实测确定，不照搬 Mac
并发。先以两任务配对测量并核对保留资源，评估并发与训练并发一起计入
负载；不能把每个任务的一核理解成连评估进程也只占一核。

输出须记录源码身份、面板、场景、算法、种子与组件哈希，并与小图分开。
当前属于开发诊断设计；正式实验仍须遵守 main 或显式 tag 的来源要求。
