# Template 1 production demo

This is local development evidence on `main` with uncommitted changes, not a
formal experiment or a performance claim. The factory is a byte-for-byte copy
of the built-in Template 1: 12 × 12, four machines, four AGVs and ten buffers.
Its geometry is symmetric; mirrored machines have different operation types.
Energy is inactive. The default normal quality mode has zero defect probability;
inspection and scrap facilities are present but need not be used in this case.

## Run and replay

From the repository root with the existing environment:

```sh
uv run --no-sync smartsom run --config configs/runs/template1_static.yaml --render-mode human
uv run --no-sync smartsom run --config configs/runs/template1_disturbed.yaml --render-mode human
```

Each execution prints its recording directory. Replay that directory with
`uv run --no-sync smartsom playback RUN_DIRECTORY`. The verified local recordings
also have stable links:

```sh
uv run --no-sync smartsom playback artifacts/template1/static-replay
uv run --no-sync smartsom playback artifacts/template1/disturbed-replay
```

The links are generated by the verification script, not shipped as repository
fixtures. On a fresh checkout, generate them with:

```sh
uv run --no-sync pytest -q tests/unit/test_production_runtime.py tests/unit/test_template1_demo.py
uv run --no-sync python scripts/validation/template1_validate.py
```

Playback starts paused. Use Play, Step +1/−1 and the bottom timeline. The right
panel gives exact cargo, storage, processing and delivery state. A pool symbol
represents occupancy, not one symbol per job.

## Cases and independent checks

Twelve initial orders repeat four routes three times: `1→2→4`, `2→1→3`,
`3→4→2`, `4→3→1`. Each route takes 4, 6 and 8 nominal processing ticks.
All orders have priority 1 and due time 600 (plus release time for later orders).
The disturbed case releases two orders at tick 40 and two at tick 80, without
advance notice. Machine 001 is down on `[20,40)`. Both limits are 2,000 ticks.

Static verification delivered 12 orders / 36 operations by tick 288. Disturbed
verification delivered 16 orders / 48 operations by tick 403, then retained the
existing dynamic-runtime semantics and ran to its 2,000-tick horizon. These are
qualified counts, not percentages. A completed horizon alone is insufficient:
the independent ledger requires every demand to be delivered exactly once.

The fixed outage happens during an idle interval under this rule. It therefore
does not extend completion time in this full run. A separate local case puts
an outage `[10,13)` inside the first operation: start 9, finish 16, four active
ticks and three paused ticks. The no-outage operation starts at 9 and ends at 13.
Processing-completion event timestamps refer to the committed boundary; do not
copy the older spatial runtime's start/end convention.

`scripts/validation/template1_audit.py` independently checks ownership and demand
conservation, facility capacities, grid bounds/obstacles, one-cell movement,
vehicle overlap/swaps, processing order/duration with outage intervals, transport
movement/interaction time and unique delivery. It does not call the simulator.
It records all three operation intervals and transport legs for orders 01–04.
Tests deliberately corrupt delivery counters, processing completion and positions
to establish that the auditor rejects these errors. Execution replay is an
additional check; it does not replace the independent ledger.

## Dispatch reference and differences

`builtin.coordinated` is a new optional rule; existing rules retain their behavior.
It follows the SO-Baseline CentralRulePolicy ideas: weighted slack priority,
persistent job/port tasks, loaded-first allocation, eight-tick space-time planning,
vertex/edge reservations and parking to release ports. Public decisions now also
include the released job's nominal remaining route. Hidden defects and future
orders remain unavailable to policies.

This is an adaptation, not an import of the old environment or its action indices.
Remaining-work priority uses nominal processing plus two interactions per remaining
transport; it does not reproduce the reference's full route-distance estimate.
The demo uses normal processing and skips inspection detours because all its
configured defect probabilities are zero. It does not reproduce the reference's
three-mode quality tradeoff. No rule result from that worktree is claimed here.
The rule is an engineering reference, not a matched-information algorithm
ablation against the learned observation projection.
Reservations are only policy plans and do not alter physical collision or capacity
arbitration. The first-step proposal is revalidated by the unchanged simulator.

## Learning

```sh
uv run --no-sync python scripts/validation/template1_train.py --seconds 21600
```

The local curriculum uses current RLlib resource PPO and role-shared 128 × 128
MLPs. It progresses through one order, static twelve orders and disturbed sixteen
orders, retaining compatible weights between separate runs. Each stage has a
262,144 adapter-decision step cap; these steps are not physical ticks. Recipes
explicitly set 128 × 128 at the experiment override layer and allow 100,000
decisions / 2,000 physical ticks per episode. This avoids the general defaults
of 64 × 64 and 1,024 decisions. An initial incorrectly resolved trial was stopped
and preserved as invalid configuration evidence. Remaining
wall time is split between remaining stages, and an update-boundary callback stops
training when the stage deadline is reached. Checkpoint saving can add overhead.
The six-hour cap is a maximum, not a promise to consume six hours. Final evaluation
is separate from training. No rule takes over during learning or inference.

Stage endpoints are compared using development execution seed 401 on both cases,
ranked by qualified deliveries then completed operations. Selection is frozen in
`selection.json` before final seeds 501–505. The final acceptance requires all
12/16 orders in every episode, independent ledger checks and replay audit.
Final evaluations use two local processes with one Torch thread each. They load
all algorithm parameters from the selected checkpoint, so trace metadata and
inference share exactly the same encoding. An existing frozen selection can be
rechecked without training using `--selection PATH/selection.json`.
`report.json` records failures as well as successes; model files alone are not
proof of an accepted learned controller. Earlier spatial checkpoints cannot be
loaded through this action/observation contract.

**Current result (2026-09-16): model not accepted.** All three 262,144-step
curriculum stages trained, but final seeds 501–505 each delivered 0/12 static
orders and 0/16 disturbed orders. The sample caps completed before the six-hour
maximum. The commands above demonstrate the verified rule controller; there is
currently no accepted learned controller to substitute. Full results and failure
diagnosis are in [the verification report](validation/template1-2026-09-16.md).
To reproduce evaluation of this failed, frozen selection (exit 1 is expected):

```sh
uv run --no-sync python scripts/validation/template1_train.py --selection artifacts/template1/curriculum-20260916T033525Z/selection.json
```
