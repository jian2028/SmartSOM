## 阶段1：输入与动作语义验收（先实际做）

使用Python3.12和锁文件，`uv sync --locked --extra cpu`，然后
`uv run pytest tests/unit/test_base_reservations.py tests/integration/test_base_ppo.py -q`。
若环境不允许安装，准确报告缺失项，不换Torch版本来声称相同复现。

对当前四组实际可达轨迹抽样（总上限四组各2000物理tick），检查：

- Dispatcher candidate与目标站点绑定，拒绝数不覆盖following字段；载货无WAIT。
- Post context自己的取货额度、承诺数与实际账本一致；不是把Pre额度当成Post额度。
- 当前工序剩余标准工作量的字段和单位正确，暂停/修复进度一致；不泄露未来故障或质量。
- WAIT只限空载无承诺/服务，退出本tick后续协商，下一tick重决策；禁止零时间无限WAIT。
- STOP-off依然逐次选择接收者，额度耗尽后停止；服务锁和实际pre空位独立检查。
- 同arm/seed网络初值相同；候选置换和空集合不破坏身份/掩码；Rule/Random动作空间匹配。
- 进一步审查工件位置标签、本站/下游站点分组、Machine候选following绑定：
  分别记录“字段存在”“表达可区分”“相同完整actor输入的实际可达别名”。
  没有可达反例不能宣称不存在问题；输入别名也不等于动作后果已证明相反。

若需临时断言/观测，放在诊断适配器里，证明插桩前后同种子同动作轨迹一致；
不热改Mac源码，不把检查脚本当策略修复。

## 阶段2：有限分支因果续跑（有真实模型/快照才执行）

最多18个有来源的快照 × 最多3个合法动作 × 4个预登记未来重复 = 216条分支总上限。
先登记来源checkpoint SHA256、arm/seed/episode、世界种子、完整动作前缀、恢复验证。
复用已核实的可重放旧证据；不要把聊天摘要当快照或模型。先做同动作恢复对照，
再只干预一次动作，后续策略/decoder冻结。涵盖早/中/尾段及正对照，不能只挑失败。
比较Buffer ACCEPT/STOP，空载Dispatcher WAIT/申请，以及会进入资源互等的取送决策。
区分严格资源闭合证明、STOP/WAIT停滞、普通到时未排空；证书必须列出占有与等待资源、
可用释放动作及为何不能释放，不能从“所有车有货”或“未排空”单独推断死锁。
完整J只在成对都排空时比较；全部分支保留交付比例、排空与未完成量。
离线分支标签不是历史on-policy advantage。报告随机流配对的实际范围与限制。

## 模型和证据交接

Git分支仅含源码、测试、文档。Mac路径和`runs/`不在云端；不要假装可直接访问。
当前首个云任务先执行阶段1并准备阶段2/3入口。没有收到验证过的模型/可重放轨迹包时，
阶段2/3标记“等待模型”，完成阶段1报告后结束任务，不循环等待消耗token，
不使用未训练网络替代中后期模型并声称完成诊断。

所需数据包格式：manifest含训练commit+source hashes、arm、seed、episode、
checkpoint SHA256、运行配置、验证面板；checkpoint含models/options（诊断不更新权重），
恢复快照附世界种子和动作前缀/RNG状态。输入包进入只读目录。另需完整学习曲线和逐seed
验证结果才能分析是否长期收益，缺失部分明确列出。

最终中文报告：环境/源码身份、各项通过数/失败证据、可达反例或未证实风险、
D2/D3完成/等待数量、事实与推测、最多一个证据支持的最小修正候选（仅建议），
下一步所需数据清单。提供机器可读清单和可运行脚本，不能只给文字结论。
保存小型报告和脚本为任务diff便于取回，不提交巨型运行产物，不自行merge/push。
